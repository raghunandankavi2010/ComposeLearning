Image delivery for low-cost phones

A system-design walkthrough of the fastimages feed — ComposeLearning

Jetpack Compose Coil 3 OkHttp 5 India-first constraints

The thesis. Showing an image is a UI problem. Showing it fast on a ₹9,000 phone on a congested cell is a systems problem, and the answer is not "download a smaller image" — it is a decision function that runs on the device, resolves capability into a small set of variant parameters, and keeps every cache layer between the phone and the blob store shareable. Screen density is the input everyone reaches for first and it is the one that misleads you most.

1. The problem and the constraints

A home-screen grid of ~120 food photos. The user opens the app, sees tiles immediately, and flings. What "good" means, in priority order:

  1. Something is on screen in the first frame. Never blank, never white, never jumping.
  2. Scroll never drops a frame, including while images arrive and decode.
  3. Bytes are proportionate to what the user can actually see and afford.
  4. Degradation is graceful: slow link, cheap device, Data Saver on, network lost mid-scroll.

The constraints that make it interesting:

ConstraintConsequence
Budget phone: 1080×2400 screen, 2–3 GB RAM, 8 slow cores, ~96 MB heap A high-density screen on a device that cannot afford high-density images. Decode CPU and bitmap memory bind before bandwidth does. One 1080×1080 ARGB_8888 bitmap is 4.4 MB of heap.
Congested cellular: 300–800 kbit/s, 200–600 ms RTT Round trips hurt more than bytes. Anything needing a second request per tile is suspect.
Metered data, Data Saver commonly enabled Speculative work is spending someone else's money. It needs an off switch driven by user intent.
Tens of thousands of Android SKUs Per-device responses are unshareable. Cache keys must describe bytes, not devices.

2. Architecture

The question interviewers push on: "why not send the device profile to the server and let it decide?" Because the response would then vary per device model. You would need Vary headers, and the CDN edge — the layer doing the most work — would fragment across tens of thousands of SKUs. Resolving locally turns that population into ~72 shared objects. Server-side device detection via User-Agent is a web-era pattern and its cost is exactly this.

3. The decision function

Everything reduces to one expression, evaluated on the device:

variant = f(layout size, density, device tier, network tier, user intent)

Why measure throughput yourself

NetworkCapabilities.getLinkDownstreamBandwidthKbps() is a radio capability hint, not a measurement — it will report "LTE, 20 Mbps" on a congested cell delivering 300 kbit/s. So throughput comes from okhttp3.EventListener.responseBodyStart/End, which brackets body bytes only. DNS, TCP, TLS and time-to-first-byte are latency; folding them into a bandwidth figure makes a fast link to a distant server look slow.

Tier flapping is a real bug, not a theoretical one. The tier feeds the URL, so every flip changes the cache key and re-downloads the visible screen. Four defences: re-classify on a 5 s timer rather than per sample; require a 25% margin to move up a tier; enforce a 10 s minimum dwell; and publish a rounded kbit/s so the policy never sees jitter that only the debug panel should see.

4. One tile's request lifecycle

Calibration beats cleverness — a war story from this very feature. The first version of this ladder used a 1.5 s read budget on a fast link, which is correct for a CDN edge returning a pre-warmed derivative in under 200 ms. The demo's backend is not that: it 302-redirects and generates the crop, measuring 1.25–1.68 s TTFB from a desktop on fibre under a 16-request burst. Every request timed out, downgraded twice, hit the cap and gave up — the feed rendered as flat colour rectangles. Two things to say about it:
  • A timeout ladder is derived from the p95 TTFB of your real backend under your own concurrency, and it is the first thing you put behind remote config: a backend regression turns an aggressive client budget into a self-inflicted outage.
  • A read timeout is not a total call budget. "Cancel anything over 1.5 s" is callTimeout / Call.timeout(); an interceptor can only shape connect, read and write. And connect must be sized separately — DNS + TCP + TLS is a fixed cost that does not scale with throughput, so folding it into the read budget lets the tighter constraint govern both.
Why downgrade instead of retry. Retrying the same variant on a link that just proved it cannot deliver it in time only spends the budget again. Asking for less is the only retry that changes the odds. The retry announces itself with a request header so the interceptor grants a longer budget — and that header is stripped before the request leaves the device, because if it reached the CDN it would fragment the edge cache key.

7. What is done to make scrolling smooth — the cancellation story

Smoothness is mostly about work you refuse to do. Four mechanisms, at four scopes:

ScopeTriggerMechanismObservable as
One tiletile scrolls out of compositionAsyncImagePainter is a RememberObserver; onForgotten disposes the requestcancelled counter
Prefetch windowdirection change / new windowsubmit() cancels the previous Job; children die with itin-flight count drops
Fling40 windows crossed in 400 ms90 ms settle delay + collectLatestonly one window is ever queued
Screennavigating awayrememberCoroutineScope cancels; loader and caches surviveno orphaned work, warm return visit
The counter-intuitive metric: a healthy fling should produce cancellations. Zero cancellations during fast scrolling means requests are outliving their views — which is both wasted bandwidth and a decode competing with the frame you are trying to draw. The panel surfaces cancelled for exactly that reason.

The other half of smoothness is bounded concurrency. Prefetches and visible cells share one OkHttp dispatcher, and HTTP/2 stream priority is not something OkHttp exposes usefully — so priority is enforced structurally instead: 3 parallel eager prefetches, 2 disk-only, nearest first, and the window shrinks on slow links and low-tier devices.

In production, every one of these is segmented by device tier × network tier. A global p50 hides the users this entire design exists for. The SLIs worth alerting on:

  • image p95 latency, per segment — not a global average
  • cache hit rate per layer: L1 memory, L2 disk, L3 CDN edge
  • bytes per session, and prefetch waste rate (prefetched but never shown)
  • time to first meaningful image on the home screen
  • timeout rate and downgrade rate — a rising downgrade rate means the timeout ladder needs remote-config surgery, not a code change

9. Trade-offs worth raising unprompted

ChoiceThe tension
AVIF vs WebPAVIF is 20–30% smaller and materially slower to decode on weak CPUs. On a low-tier device it can cost more in decode than it saves in transfer. "Fewer bytes" and "faster" are not the same thing. Gate it on tier and A/B test — do not enable it globally because a blog post said it is smaller.
HARDWARE vs RGB_565Mutually exclusive. Hardware bitmaps keep pixels out of the Java heap but cost ~1 FD each and forbid pixel access; RGB_565 halves heap but is software and wrong wherever alpha exists. Many teams keep hardware everywhere and cap the bucket instead — the lever that cuts transfer and decode at once.
BitmapPool / inBitmapDo not add this. Correct advice in the Glide/Fresco era; obsolete now. ART's generational GC made short-lived bitmap allocation cheap, inBitmap requires software bitmaps (so a pool forces allowHardware(false) — trading the big win for a small one), and hardware bitmaps cannot be pooled at all because their pixels live in graphics memory. Coil removed its pool deliberately.
Bucket granularityFewer buckets means a hotter edge cache and a smaller derivative cache, but more over-fetch per device. More buckets is the reverse. It is a cache-efficiency vs byte-efficiency dial, and it belongs in remote config.
Prefetch aggressivenessEvery prefetch is a bet placed with the user's data allowance. Track the waste rate; if it is high you are buying latency with someone else's money.
Quality-tiered URLsMaking quality part of the URL means a network change changes the cache key. That is why the never-downgrade ledger exists — without it, adaptivity actively harms the user who just walked out of WiFi.
Timeout aggressivenessAn aggressive budget converts a slow backend into a failed one, and the retry it triggers makes the congestion worse. Calibrate from measured p95 TTFB, keep it in remote config, and make failure downgrade rather than repeat. Also instrument the downgrade rate — a rising one is the early warning that the budget no longer matches the backend.
Separate LQIP requestRejected. On a 400 ms-RTT link, a second request per tile doubles round trips before anything is visible. A hash that rides in the catalog JSON is close to free.

12. If you get 60 seconds to answer

"We never send the master image and we never send device info. The client measures its cell width, classifies the device from RAM and heap and the network from measured throughput, and folds those into three URL parameters — width bucket, quality, format. Buckets keep the CDN edge and our disk cache shareable across the whole device population. A dominant colour and a 30-byte blur hash ride in the catalog JSON so the first frame is never empty and the aspect ratio is known before any byte arrives. We prefetch two tiers ahead in the direction of travel — decoded for the next six, bytes-only for the twelve after that — and cancel the window on direction change. On a low-tier device the binding constraint is decode CPU and bitmap memory, not bandwidth, so the cache budget is a share of the heap and the prefetch window halves. Timeouts are per-call and adaptive; on expiry we ask for a smaller variant rather than retrying the same one. And we measure the cache split, the fetch/decode split and the cancellation rate, segmented by tier — because a global p50 hides exactly the users this design is for."
